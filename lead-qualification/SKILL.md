# Lead Qualification

## Goal

Квалифицировать входящий лид по переписке без допроса клиента и без выдумывания данных. Извлекать уже сообщённые факты, использовать контекст объявления, определять один лучший следующий вопрос и возвращать структурированный результат для n8n/amoCRM.

Не заменять навыки общения, расчёта цены, точного определения модели товара или записи в amoCRM. Этот навык решает только задачу квалификации и подготовки данных.

## Expected input

Использовать всё, что уже доступно агенту:

- последнее сообщение клиента;
- историю диалога;
- заголовок и описание объявления Avito;
- текущие поля сделки amoCRM;
- уже определённый товар/модель, если их передал другой навык;
- источник/аккаунт и ссылку на чат, если они есть.

Никогда не просить клиента повторять информацию, которая уже есть в переписке, объявлении или CRM.

## Qualification fields

Собирать и нормализовать:

- `category` — категория товара;
- `model` — конкретная модель;
- `quantity` — количество;
- `city` — город клиента/доставки;
- `payment` — способ оплаты;
- `expectation` — срок/готовность ждать/срочность;
- `budget_rub` — бюджет клиента, только если он сам его сообщил или вопрос о бюджете действительно нужен;
- `phone` — номер телефона для передачи менеджеру.

Дополнительно фиксировать признаки:

- вопрос о цене;
- запрос скидки;
- срочную доставку;
- запрос технической совместимости;
- явную готовность купить;
- сомнительное или спамное обращение.

## Payment normalization

Нормализовать только при достаточной уверенности:

- `Наличка` — наличные, нал, наличкой;
- `Безнал без НДС` — только если клиент явно говорит про безнал без НДС;
- `С НДС` — оплата с НДС;
- `Безнал ИП` — оплата на ИП / безнал на ИП;
- `US DT` — USDT, US DT, крипта USDT.

Если клиент пишет только «безнал» и нельзя понять вариант, не угадывать. Оставить `payment: null` и уточнить позже.

Всегда писать `US DT` через пробел.

## Core workflow

1. Прочитать всю доступную историю, CRM-контекст и контекст объявления.
2. Извлечь только подтверждённые факты. Не путать цену объявления с бюджетом клиента.
3. Если модель или категория однозначно следуют из объявления и клиент не переключился на другой товар, использовать контекст объявления вместо повторного вопроса.
4. Если модель неоднозначна, не придумывать точную модификацию. Зафиксировать неопределённость и запросить уточнение либо передать задачу навыку определения товара.
5. Сформировать `crm_patch` только из данных, которые можно безопасно записать без предположений.
6. Определить, чего не хватает для следующего шага.
7. Выбрать только ОДИН следующий вопрос клиенту. Не отправлять анкету из нескольких вопросов.
8. Если нужен человек, выставить `handoff.required = true` и объяснить причину.
9. Вернуть результат строго по JSON-схеме ниже, без дополнительного текста.

## Question priority

Выбирать вопрос по контексту, а не механически.

Приоритеты:

1. Если клиент спрашивает цену, скидку, наличие или явно готов купить и телефона ещё нет — запросить телефон.
2. Если непонятно, какой именно товар нужен — уточнить модель/модификацию.
3. Если для сделки критично количество — уточнить количество.
4. Если форма оплаты влияет на коммерческое предложение — уточнить оплату.
5. Если важны доставка/срок — уточнить город и ожидание.
6. Бюджет спрашивать только когда это действительно помогает подобрать решение; не превращать любой лид в BANT-анкету.

Не задавать клиенту больше одного нового квалификационного вопроса за один ход, кроме естественной короткой связки вроде «Какой город и сколько штук нужно?» когда эти два поля неразделимы для запроса клиента.

## Hard rules

- Не сообщать цену в сообщении клиенту. На вопрос о цене рекомендовать запрос телефона; финальную формулировку может сделать навык общения.
- Не обещать сроки доставки без подтверждённых данных.
- Не придумывать наличие, комплектацию, гарантию, совместимость или скидку.
- Не считать скидку согласованной без подтверждения человека.
- Не считать номер из подписи/системного поля телефоном клиента, если он не относится к контакту сделки.
- Не перезаписывать заполненное поле CRM новым менее уверенным значением.
- Не очищать существующие CRM-поля из-за отсутствия данных в новом сообщении.
- Не задавать повторно вопрос, на который клиент уже ответил.

## Human handoff

Устанавливать `handoff.required = true`, если:

- клиент просит скидку или индивидуальные условия;
- клиент требует точный нестандартный срок доставки, который нельзя подтвердить;
- техническая совместимость не подтверждается доступной базой знаний;
- клиент конфликтует, предъявляет претензию или требует руководителя;
- есть противоречивые данные, способные привести к неверному коммерческому предложению;
- клиент явно готов оформить заказ и передача менеджеру уже предпочтительнее дальнейшей автоматической квалификации.

Не помечать handoff только потому, что одно второстепенное поле не заполнено.

## Status rules

Использовать одно из значений:

- `new` — недостаточно данных, только первое/общее обращение;
- `qualifying` — есть реальный интерес, но нужны дополнительные данные;
- `qualified` — товар/потребность понятны и данных достаточно для осмысленной работы менеджера;
- `handoff` — требуется человек сейчас;
- `disqualified` — явный спам, нецелевое обращение или отсутствие коммерческого интереса, подтверждённое контекстом.

Не дисквалифицировать лид только за короткий, неграмотный или странно сформулированный вопрос.

## Output

Всегда возвращать валидный JSON и ничего кроме JSON:

```json
{
  "status": "new|qualifying|qualified|handoff|disqualified",
  "intent": "buy|price|availability|delivery|compatibility|question|other",
  "facts": {
    "category": null,
    "model": null,
    "quantity": null,
    "city": null,
    "payment": null,
    "expectation": null,
    "budget_rub": null,
    "phone": null
  },
  "crm_patch": {},
  "missing": [],
  "next_step": {
    "action": "ask_phone|ask_field|handoff|none",
    "field": null,
    "question": null
  },
  "handoff": {
    "required": false,
    "reason": null
  },
  "flags": {
    "price_question": false,
    "discount_request": false,
    "urgent_delivery": false,
    "compatibility_uncertain": false,
    "strong_buying_intent": false
  }
}
```

### `crm_patch` rules

Использовать понятные бизнес-ключи:

- `Категория`
- `Модель`
- `Кол-во`
- `Город`
- `Оплата`
- `Ожидание`
- `Бюджет`
- `Телефон`

Добавлять ключ только если значение подтверждено и его безопасно записывать. Не отправлять `null` для очистки поля.

## Quality check

Перед возвратом результата проверить:

- все ли уже известные поля извлечены;
- не был ли задан повторный вопрос;
- не перепутан ли бюджет с ценой объявления;
- не угадана ли модель или форма оплаты;
- есть ли только один основной следующий вопрос;
- нужен ли телефон сейчас;
- не требуется ли человек;
- содержит ли `crm_patch` только безопасные обновления;
- является ли результат валидным JSON.

## Canonical categories

Всегда использовать точные русские названия категорий для amoCRM.

Нормализовать:

- GPU, видеокарта, графический ускоритель, NVIDIA RTX, NVIDIA A-series,
  Tesla, A100, H100, H200 и аналогичные товары → `Видеокарты`
- CPU, процессор, Xeon, EPYC, Ryzen, Threadripper → `Процессоры`
- RAM, DDR4, DDR5, RDIMM, UDIMM, ECC → `Оперативная память`
- Ноутбук, laptop → `Ноутбуки`
- Сервер, server → `Серверы`

Не возвращать английские категории вроде `GPU`, `CPU`, `RAM`.
Использовать только каноническое значение категории.

## Price question rule

Если клиент спрашивает цену и номер телефона ещё неизвестен,
`next_step.question` должен быть ТОЧНО:

"Цены актуальные, отправьте номер телефона."

Не перефразировать.
Не добавлять приветствие.
Не добавлять объяснение.
Не писать "подготовим расчёт".
Не добавлять дополнительные вопросы.
