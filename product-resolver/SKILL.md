# Product Resolver

## Goal

Определять, какой товар имеет в виду клиент, и приводить упоминание к безопасному каноническому названию.

Не придумывать объём памяти, поколение, суффикс, модификацию, процессор, видеокарту или другую характеристику, если она не подтверждена контекстом или каталогом.

## Expected input

Использовать доступные источники в таком порядке приоритета:

1. точное совпадение с товарным каталогом/таблицей, если каталог передан агенту;
2. явное текущее сообщение клиента;
3. заголовок и описание объявления Avito;
4. история текущего диалога;
5. уже заполненные поля amoCRM, если клиент им не противоречит.

Если клиент явно переключился на другую модель, новое явное упоминание имеет приоритет над моделью объявления и старым значением CRM.

## Canonical categories

Использовать точные русские значения:

- GPU, видеокарта, графический ускоритель, NVIDIA RTX, NVIDIA A-series, Tesla, A100, H100, H200 и аналоги → `Видеокарты`
- CPU, процессор, Xeon, EPYC, Ryzen, Threadripper → `Процессоры`
- RAM, DDR4, DDR5, RDIMM, UDIMM, ECC → `Оперативная память`
- ноутбук, laptop, Legion, ROG, TUF, OMEN, Nitro, Predator, Katana и аналоги → `Ноутбуки`
- server, сервер → `Серверы`

Если категория не подтверждается безопасно, вернуть `category: null`. Не придумывать новую категорию.

## Resolution workflow

1. Извлечь последнее явное упоминание товара клиента.
2. Определить категорию по модели, контексту объявления и каталогу.
3. Нормализовать регистр, пробелы, дефисы, `GB/ГБ`, производителя и очевидные алиасы.
4. Если есть точное совпадение в каталоге, использовать точное название из каталога.
5. Если точного совпадения нет, нормализовать только подтверждённые части модели.
6. Если одна строка может означать несколько товаров, не выбирать наугад. Вернуть `resolution: "ambiguous"` и кандидатов.
7. Если данных недостаточно даже для кандидатов, вернуть `resolution: "unknown"`.
8. Формировать `crm_patch` только при достаточно высокой уверенности.
9. Возвращать только JSON по схеме ниже.

## Safe normalization rules

Допустимо:

- `A5000`, `RTX A5000`, `Nvidia A5000` → `RTX A5000 24GB`, только если контекст однозначно про NVIDIA RTX A5000 и объём 24GB подтверждён каталогом или надёжным справочным соответствием.
- `H200 141`, `H200 141gb`, `Nvidia H200 141GB` → `NVIDIA H200 141GB`.
- `3080 ti` → `RTX 3080 Ti`, но не добавлять объём памяти без подтверждения.
- `7955wx` → `Threadripper PRO 7955WX`, если контекст однозначно про процессор AMD Threadripper PRO.

Недопустимо:

- превращать `A6000` в конкретную модификацию с памятью, если она не подтверждена;
- считать `3080` и `3080 Ti` одной моделью;
- считать `H100` и `H200` одной моделью;
- считать `A100 40GB` и `A100 80GB` одной моделью;
- добавлять `Ti`, `SUPER`, `PRO`, `Max-Q`, объём VRAM, сокет, частоту или поколение по догадке;
- подменять модель объявления, если клиент явно спросил другую модель.

## Catalog behavior

Если агенту доступен каталог или Google Sheet:

- сначала искать точное совпадение по модели и алиасам;
- затем искать по ключевым токенам модели;
- при нескольких похожих строках не выбирать только по похожести;
- считать точное совпадение каталога сильнее общей модели знаний;
- возвращать точное название каталога в `resolved_model`.

Если каталога нет, не утверждать наличие товара. Этот Skill определяет модель, а не наличие.

## Confidence

Использовать `confidence` от `0.0` до `1.0`.

Рекомендации:

- `0.95–1.0` — точное совпадение каталога или однозначная полная модель;
- `0.85–0.94` — безопасная нормализация известного алиаса;
- `0.60–0.84` — вероятная модель, но есть недостающая модификация;
- `<0.60` — не записывать модель в CRM.

Добавлять `Модель` в `crm_patch`, только если `confidence >= 0.85` и `resolution` равен `exact` или `normalized`.

Добавлять `Категория` в `crm_patch`, только если категория подтверждена.

## Ambiguity handling

Если клиент пишет несколько вариантов, например `A5000 или A6000`, не выбирать один как основной без дополнительного контекста.

Вернуть:

- `resolution: "ambiguous"`;
- `resolved_model: null`;
- список `candidates`;
- `needs_clarification: true`;
- короткий `clarification_question`.

Задавать только один уточняющий вопрос.

## Output

Всегда возвращать валидный JSON и ничего кроме JSON:

```json
{
  "resolution": "exact|normalized|ambiguous|unknown",
  "category": null,
  "raw_mention": null,
  "resolved_model": null,
  "brand": null,
  "confidence": 0.0,
  "candidates": [],
  "needs_catalog_lookup": false,
  "needs_clarification": false,
  "clarification_question": null,
  "crm_patch": {},
  "evidence": []
}
```

## Output field rules

`evidence` использовать только для коротких проверяемых фактов, например:

- `"Явно указано H200 141GB"`
- `"Контекст объявления: видеокарта"`
- `"Точное совпадение с каталогом"`

Не писать длинные рассуждения.

`crm_patch` может содержать только:

- `Категория`
- `Модель`

Не обновлять другие поля CRM этим Skill.

## Quality check

Перед возвратом проверить:

- не перепутана ли модель с похожей;
- не добавлены ли неподтверждённые характеристики;
- не проигнорировано ли явное переключение клиента на другой товар;
- совпадает ли категория с каноническими значениями;
- достаточно ли уверенности для записи в CRM;
- не требуется ли уточнение;
- является ли результат валидным JSON.
